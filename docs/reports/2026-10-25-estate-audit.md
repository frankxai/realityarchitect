# Reality Architect — related-system audit

Observed 25 October 2026. Scope: repository metadata, public source contracts, approved architectural boundaries, and narrowly scoped repository documentation. No personal vault, chat history, intimate reflection, credentials, or real personal evaluation queries were ingested. Built on SIP.

This is a product-source audit, not a replacement Registry, provider benchmark, deployment receipt, or customer-use claim. Repository README claims are not treated as executed tests.

## Decision

Keep the daily personal experience, file standard, deterministic engine, exports, and portable practice in `realityarchitect`. Reuse its existing pinned Starlight kernel contract. Do not move the engine to the similarly named scaffold repository or require Starlight to run an ordinary person's daily practice.

Sovereignty is a product constraint: the person's canonical records stay under their control. External memory providers and knowledge graphs remain optional projections with no authority to change the person's contracts. No new graph or vector service is justified by this inspection.

## Boundaries and discovered contradictions

1. **Registry versus runtime.** The Registry is portfolio authority; product repositories own product source. Memory, MCP, Notion, Drive, and provider state are projections or evidence inputs. A semantic match cannot authorize a change to ownership or an accepted architecture decision.

2. **Old scaffold versus accepted implementation.** The 4 October North Star proposed eventually moving format tooling into `reality-intelligence-systems`. The accepted [ADR-002](../adr/ADR-002-reality-architect-and-starlight.md) puts the standalone engine and contract-only coupling in this repository. The current scaffold contains no countervailing implementation. Keep the engine here.

3. **Design pack versus evolved product.** The central [brand pack](https://github.com/Starlight-Intelligence/starlight-design-intelligence/blob/851a11be31a0640df64baabcf2b1fc1afb9ce849/brand-packs/reality-architect/BRAND.md) still describes only the AI systems assessment. Local `DESIGN.md`, `TASTE.md`, and `AGENTS.md` already support the labeled Meaning register and dawn typography. The current mission explicitly confirms life architecture and personal meaning. Preserve quiet editorial hierarchy and exact artifacts; propose a central pack reconciliation rather than reverting the product to the older assessment framing.

4. **Life Atlas versus public Starlight Atlas.** Shared naming does not make them one corpus. A person's Atlas is private person-level state. Starlight Knowledge Tree's authored Atlas is a public research/capability corpus. Private goals or identity evidence cannot become public graph nodes automatically.

5. **Library software versus source ownership.** [Library OS](https://github.com/frankxai/library-os/blob/e41d27bb67a9d38c935e4a5831fd6ae1fb1b3b99/docs/schema.md#source-aware-public-projection) distinguishes raw private captures, verified source passages, original interpretation, and reviewed public publication. Reuse this distinction for practice sources. It does not justify publishing full copyrighted sources or a user's reflections.

6. **Signing versus occurrence.** SIS [DSSE source](https://github.com/frankxai/Starlight-Intelligence-System/blob/e036722345a5ca1347dc12d12c5067295403348c/protocol/lib/dsse.mjs) provides Ed25519 attestation primitives. A signature can bind a payload to a key and detect alteration. It cannot independently prove an event happened or establish trusted recording time. Do not promote a signed self-report into independently verified evidence.

## Reusable data contract

Keep the existing `reality.md`, `soul.md`, and `reality/` layout. The pinned kernel already represents objects, future branches, diffs, plans, receipts, and events. Its [upstream accepted ADR-000](https://github.com/frankxai/Starlight-Intelligence-System/blob/e036722345a5ca1347dc12d12c5067295403348c/docs/reality-architecture/ADR-000-reality-architecture-substrate-map.md) requires evidence on real/observed fact relations and prevents desired outcomes becoming real without a receipt or explicit unverifiable state.

Backward-compatible additions should retain, rather than collapse:

- desired/planned state; human report; direct observation; independent verification; inference; personal meaning;
- source identity and revision; occurrence time and recording time; privacy and retention class;
- correction/supersession links; original evidence and derived interpretation;
- explicit audience and per-export consent; execution actor/tool and verification receipt.

The existing `alliance` projection is deliberately narrow. Titles of shared aims, reps, moves, and done-whens can still contain sensitive text, so review the exact outgoing payload. Revocation can stop future projection; it cannot recall a file already received.

## Privacy acceptance required before release

- Manual entry and import stay local; errors, telemetry, issue bodies, and browser URLs contain no reflection content.
- Imported text is data, never tool or system authority. Instruction-shaped source content cannot expand permissions or authorize writes.
- The person approves changes to identity/values and snapshots. Imported calendar or repository metadata does not become completion or attendance evidence.
- Export previews name the actual audience and files. Unknown or invalid audience fails closed. Private-field canaries never enter shared projections, including sort keys, hashes, or identifiers.
- Deterministic imports retain provenance and deduplicate by stable source event identity. A correction does not quietly erase the original.
- Corrupt/unsupported imports leave existing local state intact. Storage denial/full errors do not claim a successful save. Deletion covers text and image stores with a recoverable confirmation flow.
- One narrow authorized connector is enough for a first proof. No claim of exhaustive ChatGPT history, every coding session, or ambient local-machine access is warranted.
